Windows에서 사용자가 로그인할 때는 한 프로그램이 모든 작업을 처리하지 않는다.   
로그인 정보를 입력받는 구성 요소, 인증을 처리하는 구성 요소, 계정 정보를 저장하는 위치가 각각 다르다.  
이 글에선 로그인 화면에서 시작한 요청이 어떻게 인증되는지, 그리고 SAM·LSASS·NTDS.dit·Credential Manager가 각각 무엇인지 정리하도록 하겠다.

## 1. 로그인 정보를 입력받는 단계 
사용자가 windows로 로그인 화면을 열면 Winlogon(로그인과 화면 잠금·해제 절차를 관리하는 시스템 프로세스)이 대화형 로그인 절차를 관리한다.  

절차는 다음과 같이 진행된다:
```bash 
1. winlogon이 LogonUI를 실행
2. LogonUI이 로그인 화면을 표시
3. Credential Provider이 비밀번호·PIN·스마트 카드 등 선택한 방식에 맞춰 로그인 정보를 수집
```

참고로 Credential Provider는 입력한 비밀번호가 맞는지 직접 판단하지 않고, 수집한 정보를 인증에 사용할 수 있는 형태로 준비해 다음 단계로 전달한다.  

## 2. LSASS가 인증을 처리하는 단계
로그인 요청은 LSASS(Local Security Authority Subsystem Service)에서 처리된다. 
LSASS는 Windows 보안 정책과 로그인 세션을 관리하며, 요청에 맞는 인증 패키지를 사용한다.

주로 사용되는 인증 패키지 종류:
```bash
로컬 계정 인증 = 주로 MSV1_0이 관여
도메인 계정 인증 = 일반적으로 Kerberos를 통해 도메인 컨트롤러와 인증 진행

# 환경과 접속 방식에 따라 NTLM이 사용되는 경우도 있음
``` 
인증에 성공하면 Windows는 사용자와 그룹, 권한 정보를 담은 접근 토큰을 만들고, 이후 파일이나 서비스에 접근할 때 이 정보를 사용한다.   

## 2-1. 로컬 계정
PC01\user 처럼 특정 컴퓨터에 만든 계정은 로컬 계정이다.   
해당 컴퓨터의 SAM(Security Accounts Manager) 데이터베이스에 로컬 사용자·그룹 정보와 비밀번호 해시가 저장된다.    

따라서 일반 Windows PC에서 SAM 파일을 발견했다면, 그 파일은 해당 PC의 로컬 계정 정보와 관련이 있다.   
SAM은 정상적인 Windows 시스템에도 존재하므로, 파일이 보인다는 사실만으로 내용을 읽을 수 있거나 취약점이 있다는 뜻은 아니다. (문제가 되는 건 권한이 없는 사람이 SAM의 내용을 읽거나 복사할 수 있을 때)  
도메인에 가입한 PC에도 로컬 계정을 위한 SAM은 존재한다.  

## 2 - 2. 도메인 계정
COMPANY\user 처럼 도메인이 관리하는 계정은 도메인 계정이다.   
이 경우 클라이언트 PC가 도메인 컨트롤러(DC)와 인증을 진행한다.  
클라이언트가 DC의 데이터베이스 파일을 직접 열어 확인하는 방식은 아니다. 

과정:
```bash
1. 사용자가 도메인 계정과 비밀번호를 PC에 입력함
2. PC의 LSASS 안에서 Kerberos 인증 패키지가 로그인 요청을 처리 (비밀번호에서 만든 키로 인증용 데이터를 암호화해 DC의 KDC에 보냄)
3. DC의 KDC(도메인 컨트롤러(DC)에서 실행되는 Kerberos 인증 서비스)는 Active Directory에 있는 해당 계정 정보를 이용해 요청을 검증 (kdc가 AD의 NTDS.dit 파일 확인 하는 과정)
4. 검증에 성공하면 DC가 TGT(티켓 발급 티켓)를 PC에 돌려줌
5. 이후 PC는 로그인 세션을 만들고, 도메인 서비스에 접근할 때 이 티켓을 사용할 수 있음
```

여기서 kdc가 검증하는 DC의 Active Directory 데이터베이스 파일이 NTDS.dit이다.   
NTDS에선 도메인 사용자뿐 아니라 그룹·컴퓨터 계정 등 여러 디렉터리 정보가 저장된다.   
따라서 일반 PC의 SAM과 DC의 NTDS.dit은 다루는 계정의 범위가 다르다.
